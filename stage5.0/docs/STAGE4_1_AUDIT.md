# Stage 4.0 技術監査（内部整理）の記録（非公開）

方針：新機能・仕様変更・バランス変更なし。整理の前後でシミュレーションの結果が同じことを、Stage 4.0 のコードと並べて確認（3つの乱数・3つの時代・約290の時点で一致）。依存：PR #13 の上に積んだ別Draft PR（#13 → #12 → #11 → main）。

## ChatGPT指摘6項目への判定
| 項目 | 判定 | 根拠（実測） |
| --- | --- | --- |
| A 長期進化の近似 | 問題あり・今回は保留（限界を記録） | 近似は跳躍1回あたり最大240ステップ（跳躍が約40万年以上では上限に張り付く。488回の平均は143ステップ）。変異2倍の根拠は無い（ゲーム上の仮定）。近似のステップでも個体は年を取るため、「跳躍中は年を取らない」という説明と食い違う。同じ3つの乱数で近似あり・なしを比べると、長寿記録は「なし」のほうが高い傾向（279対212、192対185、209対209）だが標本が少なく、「根拠不足」。生き残る系統数は同じ（3）。近似モデルの変更は別課題 |
| B セーブ・ロード | 部分的に問題あり：破損対策は修正済み／復元時間は保留 | 保存は設定＋操作ログ（約270バイト）で肥大しない。再生は決定的（近似の最中に保存しても同じ状態に戻ることをテスト）。復元時間は元の実行時間とほぼ同じ（80,000ステップ：復元32秒、元の実行30秒。全歴史277,300ステップなら約2分）。これは「ログ再生」方式の性質で、チェックポイント（エンジン状態の保存）は閉包の状態が多く、別課題として設計を残す。破損セーブは理由つきで拒否し、再生中の例外で読み込み画面に固まらないよう修正 |
| C 8系統固定 | 問題なし（仕様）／多様性の限界は保留 | 系統数は増えない（8固定）。枝は出来事の記録（タグ）で追跡し、系統樹とエンジンの記録の一致はテスト済み。系統数を16にしても計算量は増えない（1500ステップ：8系統1.3秒、16系統1.1秒）。動的な系統管理は必要性が確認できず保留 |
| D 高速進行中の処理 | 問題あり・修正済み | 実バグ：「次の出来事まで」が、記録が400件を超えると新しい出来事を検知できなかった（配列の前を削るため、添字で「新着」を数えていた）。連番方式に修正。毎フレームのDOM書き換えは47回/秒→15回/秒。長い処理（100ms超）は10回→0回 |
| E 個体数上限 | 問題なし | 上限6000に対し、30,000ステップのピークは546で一度も作動しない（capHit=false） |
| F コード構造 | 保留 | 計算の中心（engine19.js）が約25%を `develop/expressGenes` に使うが、これは計算そのもの。ゲーム層は5%未満。旧画面の関数（四象限・単位表示など）は旧セーブ用に必要で削除しない。大きさだけを理由とした分割はしない |

## 独自に見つけた問題
- 【修正】「次の出来事まで」が記録400件超で止まらない（D）。
- 【修正】近似進化が1回の呼び出しで最大240ステップ進み、画面が最大190ms止まっていた。小分けにして後続の呼び出しに分散（順序は不変。Stage 4.0と結果が一致）。
- 【修正】進化の通知が記録400件の約半分を占め、世界の出来事が流れていた。長いゲームでは、通知の頻度を制限し、背景の移入は再侵入だけ記録し、あふれたときは騒がしい種類から消す。
- 【修正】同じ名前の別形態が図鑑に並んだ（6軸のうち3つだけ名前に出るため）。重複する名前には番号をつける。
- 【修正】円盤を毎フレーム28,000画素ぶん描き直していた。再計算した（25ステップごとの）ときだけ描き、ノイズ表は一度だけ作る。
- 【修正】イベントの状態表（evoSeen/evoY）が増え続ける。エンジンの一覧から消えた出来事は忘れる。
- 【確認・問題なし】メモリリーク：80,000ステップまで、GC後のヒープは13〜15MBで平坦。乱数：シミュレーションに Math.random/Date は無し。数値精度：世界の年は倍精度で、最大約8×10^9年でも問題なし。保存と実行状態：近似の最中を含め、保存→読込で一致。
- 【記録のみ】`secSmooth`（円盤の扇の平滑化）は計算しているが使っていない。近似のステップが個体を老化させる（A）。
